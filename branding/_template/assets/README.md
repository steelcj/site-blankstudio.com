# Brand assets for this client

Drop the client's brand images in this directory. The build copies it to
`/assets/` on the site, so keep the filenames — they are fixed slots the
template references by name. Full details are in the asset specification:
`docs/en/docs/guides/branding/asset-specification--branding-images-slots-and-social-v0-1-0.md`.

Required (the build warns until these exist):

- `favicon.png` — browser tab icon (PNG, 48×48 or larger)
- `logo-lockup-dark.png` — dark logo for light backgrounds (loader, nav)
- `logo-lockup.png` — light logo for the dark footer

Recommended:

- `og-default.jpg` — social share image (raster, 1200×630)

Section imagery (optional, one per page):

- `about-work.jpg`, `contact-talk.jpg`, `audit-review.jpg`,
  `services-life.jpg`, `blog-featured.jpg`

Proof logos (optional):

- `logos/<name>.png` — client or portfolio marks for the home-page marquee

## Type

The fonts are **not** in this directory. Type is declared in `../fonts.yaml`,
and webfonts are downloaded into the built site — dropping a `.woff2` in here
does nothing, because nothing reads it. It is written up beside the images
because type is a brand asset like the logo, and this is where you come looking.

### Two halves that have to agree

`fonts.yaml` answers two separate questions, and the easy mistake is to change
one and forget the other:

| Block | Answers | Lands in | Regenerated by |
| --- | --- | --- | --- |
| `tokens:` | what the site is **set in** | `src/css/brand.css` | `npm run build:brand` |
| `families:` | what has to be **downloaded** | `src/css/fonts.css` + `src/assets/fonts/` | `npm run build:fonts` |

One file, two commands. Change `tokens` alone and you need `build:brand`;
change `families` alone and you need `build:fonts`; change both and you need
both. `npm run build` runs `build:brand` for you, but never `build:fonts` —
downloading is deliberate, it needs the network.

Neither way of getting it wrong is loud in the browser:

- **In `families`, named by no token** — the file downloads and ships, and no
  rule ever asks for it. Every reader pays for a font they are never shown.
- **Named by a token, missing from `families`** — nothing downloads, and the
  browser falls through to the next font in the stack. The page looks *fine*,
  just not the way it was designed. This is the one that survives review.

`npm run check:brand` compares the two blocks and reports both, so neither has
to be caught by eye:

```
[check:brand] warning (example.com): fonts.yaml tokens.head is set in 'Poppins',
  but no `families` entry downloads it — readers get the next font in the stack
  instead, and the page looks fine while being wrong
```

These are warnings, not errors: the build still passes. A token naming a face
nobody downloads is perfectly valid — that is exactly what the system-font
recipe below is — so the check reports and leaves the judgement to you. It
knows the CSS generics and the common system faces (`system-ui`, `Segoe UI`,
`Menlo`, `Georgia`, …) and stays quiet about those.

Family names must match the provider's spelling exactly, capitals included:
`Inter Tight`, never `Inter tight`.

### The three slots

`tokens` has exactly three, and each is a complete CSS stack — the fallbacks
matter, since they are what a reader sees while the webfont loads (and forever,
if it fails):

- `head` — headings and display type
- `body` — running text
- `mono` — code, labels, and the small-caps detail work

The nested quotes are the fiddly part. Quote each multi-word family name
*inside* the stack — CSS tolerates them bare, but the convention is quotes, and
anything with a digit or punctuation in the name requires them. Wrap the whole
value in single quotes so the doubles inside survive YAML:

```yaml
tokens:
  head: '"Inter Tight", "Inter", system-ui, sans-serif'
  body: 'system-ui, sans-serif'
```

Generic keywords — `system-ui`, `sans-serif`, `ui-monospace`, `monospace` — are
never quoted; quoting one turns it into a search for a font by that name.

### Declare only the weights the CSS asks for

The stylesheets in this template use **400, 500, 600, and 700**, and no italics
at all. A weight or style beyond that list downloads a file that no rule can
ever use — the shipped default does exactly this, declaring `Inter Tight: 800`
and fetching two files nobody sees.

Cost is one file per family × weight × subset. With both `latin` and
`latin-ext` on, every weight you add is two more files.

If you add CSS that wants a weight, add the weight here too — the pair moves
together, in both directions.

### Recipes

**System fonts — nothing to download, nothing to wait for.** The fastest and
most accessible option, and what the `vishpala.com` client ships:

```yaml
tokens:
  head: 'system-ui, sans-serif'
  body: 'system-ui, sans-serif'
  mono: 'ui-monospace, SFMono-Regular, Menlo, monospace'
families: []
```

**One family for headings, the reader's own font for text.** Most of the brand
character, a fraction of the payload — four files instead of the default's
twenty:

```yaml
tokens:
  head: '"Inter Tight", system-ui, sans-serif'
  body: 'system-ui, sans-serif'
  mono: 'ui-monospace, SFMono-Regular, Menlo, monospace'
families:
  - name: Inter Tight
    weights: [600, 700]
    styles: [normal]
```

**Webfonts throughout.** The template default — see `../fonts.yaml`. Trim its
`800` before you use it.

### Changing the type, start to finish

1. Edit `tokens` and `families` in `../fonts.yaml` **together**.
2. Check they agree: `npm run check:brand`. No network, instant, and it catches
   the half-finished edit before anything downloads.
3. Preview: `npm run build:fonts -- --dry-run` — lists every file it would
   fetch and writes nothing. (It still asks the provider what exists, so it
   needs the network.) Read the list back against your `families`; a surprise
   in it is a mistake in the YAML.
4. Download: `npm run build:fonts`.
5. Apply the stacks: `npm run build:brand`.
6. Check `src/css/brand.css` for the `--font-head` / `--font-body` /
   `--font-mono` you expect, then `npm run build` and look at a page.
7. Commit the YAML *and* the generated `brand.css`, `fonts.css`, and
   `src/assets/fonts/` together. They are outputs — never hand-edit them.

### Fonts you cannot get from Google

`provider:` accepts `google` and nothing else, so a purchased or custom face
has no path through this pipeline today. Until it does, the workaround is to
hand-place the `.woff2` under `src/assets/fonts/`, add the `@font-face` rules,
and name the family in `tokens` — accepting that `build:fonts` rewrites
`src/css/fonts.css`, so those rules cannot live there.

## Logos, and the text a screen reader speaks

A logo is a picture of a name. Something has to say that name in words, and
there are more places to say it than there are that work.

### Where the words come from

The header and footer build the logo's `alt` text themselves:

    site.yaml `name`  +  the locale bundle's `logoHome` pattern

`{name} home` in English, `Accueil {name}` in French. The pattern is in the
bundle because the two languages do not order the words the same way; the name
is in `site.yaml` because it is a fact about the client, not a translation.

So a correctly configured client needs to do nothing here. Set `name` in
`site.yaml` and the logo is named in every language.

Override it with `logos.alt` only when the mark carries words the name does not
— an abbreviation, a former name, a mark with a slogan drawn into it.

### Do not write the name into the logo file

An `<img>` element does not expose anything inside the file it loads. A
`<title>`, a `<desc>` or an `aria-label` in the SVG is not spoken, is not read,
and cannot be translated by anything in this repository. The page's `alt` is
the only string a reader hears.

Which is how a rebranded site kept announcing its old name: the string lived in
a locale bundle instead of in `site.yaml`, and no one saw it, because it is
never on the screen.

### What the file should still carry

Give the file a `<title>` anyway. It costs one line, it is what a reader sees
if they open the file directly, and it is what starts working the day the mark
is inlined into the page instead of loaded as an image.

    <svg role="img" xml:lang="en" aria-labelledby="logo-title" …>
      <title id="logo-title">Example Studio</title>

Three rules:

- **`<title>` first, always.** It has to be the first child element.
- **Never `aria-label` as well.** It overrides `<title>`, so the file then
  holds the same name twice with one copy dead. Use one — the SVG element, not
  the ARIA attribute.
- **`xml:lang` on the root.** A file that declares its language can be handed
  to a translator. One that does not is a guess.

Use `<desc>` for a picture that needs more than a name — an illustration, a
diagram. Not for a logo; a logo's name is its description.

### Words drawn into the picture

A `<text>` element inside an SVG is a shape. No build translates it.

That is fine for a **name**, which is the same in every language. It is not
fine for a **slogan**, which is a sentence, and a sentence gets translated. A
slogan drawn into a mark is a mark only one language can read.

If words in an image must change by language, do one of these:

| Method | When |
| --- | --- |
| One file per locale | The drawing itself differs by language. |
| Inline the SVG, template the text | The shapes are the same; only words change. |

Do **not** reach for SVG's own `<switch>` / `systemLanguage`. It keys off the
browser's language settings, and this site's language comes from the URL
(`/en-ca/`, `/fr-ca/`). A French reader with an English browser would get the
English drawing on a French page — the two would disagree, and the page would
be the one that is wrong.
